# Separate owner enrollment: Grok parity

Source preparation does not grant access. Grok needs a distinct bearer/principal,
the existing central executor and its original-host routes, not Eddie's bearer
and not a command-enabled instance of the isolated read-only trial.

## Supported source path

`prepareOwnerEnrollment` in `packages/control-plane/src/prepare-owner-enrollment.ts`
accepts validated local policy, current central policy, sponsor/executor IDs,
a separately custodied bearer **hash**, an expiry and one stable request UUID.
It returns proposed local/central policies and the exact admission request.
It performs no IO, creates no credential and never enables a service.

The new local principal receives the sponsor's existing read/command/session and
inbox capabilities, including its explicit budget and runtime-mode limits. It
receives no existing subscription, callback registration, inbox record or receipt.
Native grant fingerprints are recomputed for its own principal. The existing
executor receives those exact fingerprints; no second executor is introduced.
Principal expiry is bounded by the sponsor and executor; native scopes also
remain bounded by the original grants. The planner does not renew any grant.

The operator stages the reviewed successor in the Worker's `AUTH_POLICY` through
the established credential/configuration lane. This is the independent approval
input: an MCP caller cannot supply a policy, role or authority in a request.
The environment change alone does not admit the new owner to durable policy.

Before preparation/apply, POST `/owner_enrollment_challenge` with `{}` as the
existing sponsor. It returns only current revision/current policy digest and
configured policy digest. Compare the current digest with the privately retained
policy used for preparation. If it differs, stop and obtain an authorized exact
policy readback through the operator lane; do not overwrite current state from a
stale file. No tokens, grant objects or host/thread contents are returned by this
challenge. A challenge is read-only and is not permission to enroll.

An existing authenticated sponsor then POSTs `/enroll_configured_owner` with:

```json
{
  "request_id": "ONE_PERSISTED_UUID",
  "principal_id": "grok",
  "executor_id": "central-edge",
  "expected_revision": 0,
  "expected_policy_sha256": "EXACT_PREPARED_POLICY_DIGEST"
}
```

The revision above is a placeholder; use the exact current durable revision.
Authentication, live revocation/expiry, expected revision, environment digest,
operational scope parity, existing-principal preservation, executor mapping,
policy mutation and receipt insertion share the existing SQLite transaction.
Only one new owner can be admitted. Migration/custody authority cannot be copied.
The selected executor may only gain the new owner's exact fingerprint mappings;
its identity, permissions, expiry, hosts and all other fields remain unchanged.
Neither this operation nor receipt lookup submits native work.

After an uncertain response, POST `/owner_enrollment_receipt` with only that same
`request_id`, using the same sponsor identity. A committed receipt is immutable
historical evidence, not activation or permission to revive a revoked owner.
Do not generate another UUID or retry an uncertain mutation blindly. Existing
`tighten_policy` remains tightening-only; this path does not weaken it.

## Exact pending operational decision

For the current MTG deployment, the proposed action is to create **one new Grok
owner bearer**, stored through the existing private custody lane, and configure
principal `grok` in `kadenco-control-plane`, fleet `mtg`, with Eddie-equivalent
access to the six existing hosts and all projects. Preserve the current central
epoch, state, native journal, executor identity, native T3 grants and callback
signing identity. Reconcile actual policy/build/expiry before apply.

The intended host set is `local`, `codex-remote-01`, `codex-remote-02`, `pve-t340`,
`pve-laptop-5520`, and `wsl-debian`. No additional host or provider is authorized.
Copy the actual current Eddie provider and creation-mode restrictions rather
than inventing defaults. Eddie's reviewed configuration includes explicit
uncapped daily command limits and permits full-access creation; parity retains
those consequences, subject to existing task authorization and human controls.
Expiry must be no later than the existing service/command deadline, currently
November 19, 2026; no renewal is part of onboarding.

The credential is not generated by this source change. Any required action-time
confirmation must name this credential, exact expiry, reviewed policy digest,
six-host/all-project scope, current full-access/uncapped implications and Grok
as the recipient. Secret transfer must use Grok's masked connector field, never
chat, argv, logs, source or an Eddie credential. No credential value belongs in
this document or the review packet.

## Promotion and rollback

1. Complete source review, authenticated secret scan, exact-head CI/security
   checks and normal merge/release gates. Use a new release identity for changed
   runtime bytes. Neither local tests nor source merge proves installed behavior.
2. Confirm the precise credential/grant action if required. Prepare policies
   against fresh current state; preserve the private originals and one UUID.
   Stage the reviewed Worker policy and reconcile admission by its receipt.
3. Update the existing single edge's validated policy and private bootstrap
   `ownerTokens` with Grok's own credential. Its map is currently read at startup;
   follow the normal managed promotion/drain procedure, keeping the native
   attempt journal and current central state. Do not run a second edge writer.
4. Point the reviewed generic HTTPS MCP ingress to that same production listener,
   retaining per-request bearer authentication. Do not inject Eddie's bearer.
   Verify Host/Origin rejection, anonymous rejection, exact tool/host scope,
   independent receipts and revocation. A quick-tunnel read trial is not a
   qualified durable production ingress. Grok's own client and any event/wake-up
   delivery remain unverified until separately exercised.
5. Only then retire the isolated read-only trial using its exact process identity.
   Never promote its independent database into a production command writer.

To withdraw access, revoke/disable **Grok only**, preserve all existing command
receipts and reconcile uncertain requests. Stop its ingress exposure without
replacing the central database, native journal or receipt history. Do not
restore a pre-enrollment database to roll back configuration. Before reverting
runtime bytes, verify recovery/schema compatibility and retain the new audit
receipt; it uses the already-supported `audit` table, not a new recovery table.
Other principals, subscriptions, pending commands and human stops stay intact.

## Evidence and limits

`spec/owner-enrollment.cases.ts` exercises actual Worker authentication and DO
SQLite admission. `spec/owner-parity.node.mts` exercises offline six-host scope
preparation and compiled production composition with official MCP and mocked
native transport, independent originators, stable UUIDs, unknown outcomes and
revocation. These are synthetic/local tests, not Grok client qualification,
production deployment, HA acceptance or proof of proactive wake-up support.
